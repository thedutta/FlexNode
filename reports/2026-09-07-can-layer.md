# FlexNode CAN layer — standing report

_2026-09-07. Explains and pressure-tests the v2 design in [`docs/can-layer.md`](../docs/can-layer.md); reasoning in [`notes/can-layer-design.md`](../notes/can-layer-design.md); board limits in [`notes/hardware-io.md`](../notes/hardware-io.md); flash in [`docs/flash-budget.md`](../docs/flash-budget.md). > **Nothing in this report, or in the spec it describes, has been exercised on a real CAN bus.** There is no adapter on the bench. Every byte count below is derived from the moteus source in this repo; every microsecond is arithmetic, not measurement.

## 1. What the layer is for, and the two rules

FlexNode makes a *node* — "one actuator plus whatever that joint needs to know about itself" — the unit CATBOT is composed from, and the same board a sellable product. The CAN layer turns thirteen boards into one machine, and it is the product's public API. Two rules follow and decide everything else:

1. **The register map is a stable, versioned, public interface.** A host written against block v2 works against every v2 node, forever. Registers are deprecated, never recycled; `0x0FF` is the version.
2. **What a node *is* may vary; what a register *means* may not.** Nodes differ in populated hardware and compiled features, never in semantics — and unpopulated, unconfigured and uncompiled are deliberately indistinguishable (all answer `kUnknownRegister`).

The layer is an addition, not a replacement: CAN-FD framing and the multiplex subframe protocol stay bit-for-bit stock moteus, which keeps `moteus_tool`, `tview`, the CAN bootloader and the Python library working. FlexNode lives in unused register space — the v1 node block at `0x080–0x0FF` and the new channel slots at `0x200+`.

## 2. The channel model, and why it beats v1

v1 assigned fixed registers per peripheral kind. That works for one robot and fails for a product: every new peripheral type or combination needs a new register range *and* a new host special case.

v2 inverts it. A node exposes up to eight **typed channel slots** at `0x200 + 0x10·slot` (slots 1–8 = `0x210–0x28F`). Every slot has the same 16-register frame: `type, caps, status, mode` at `+0..+3`, commands `cmd_a/b/c` at `+4..+6`, measurements `meas_a/b/c/d` at `+7..+A`, a `nonce` at `+B`, four type-specific. The host discovers each slot's `type` at boot and drives every channel through one driver. A new peripheral is a new enum value, not a new register range.

**The stride is the point.** Subframes address *consecutive* registers, so a full command is one write subframe and a full readback one read subframe. Here is the wire cost for a node with a BLDC axis, a load cell in slot 1 and an I²C encoder in slot 2, both on the fast lane. Subframe headers pack a count of 1–3 into the low two bits; a count of 4 costs a byte (`moteus_multiplex.h:646`). Registers above `0x7F` are two-byte varuints (`0x217` → `97 04`).

**Command frame, host → node 5, reply requested.** CAN id `0x8005`.

| # | Bytes | Meaning | Size |
|---|---|---|---|
| 1 | `01 00 0A` | write int8 ×1 @ `0x000`: mode = position | 3 |
| 2 | `07 20 pp pp vv vv tt tt` | write int16 ×3 @ `0x020`: position, velocity, ff-torque | 8 |
| 3 | `14 04 00` | read int16 ×4 @ `0x000`: mode, position, velocity, torque | 3 |
| 4 | `13 0D` | read int8 ×3 @ `0x00D`: voltage, temperature, fault | 2 |
| 5 | `14 04 97 04` | read int16 ×4 @ `0x217`: load-cell `meas_a..d` | 4 |
| 6 | `14 04 A7 04` | read int16 ×4 @ `0x227`: encoder `meas_a..d` | 4 |
| | | **Total → DLC 24** | **24** |

**Reply frame, node 5 → host.** CAN id `0x0500`.

| # | Bytes | Meaning | Size |
|---|---|---|---|
| 1 | `24 04 00` + 8 | mode, position, velocity, torque | 11 |
| 2 | `23 0D` + 3 | voltage, temperature, fault | 5 |
| 3 | `24 04 97 04` + 8 | force, d/dt, raw counts, **contact flag** | 12 |
| 4 | `24 04 A7 04` + 8 | angle, rate, —, magnet AGC | 12 |
| | | **Total 40 → DLC 48** (8 B padding on the wire) | **40** |

Three things the example teaches that the spec's prose does not:

- **Input-only channels have no command subframe.** The spec's "axis + 2 fast channels = 32 B / 32 B" assumed symmetric command+readback. A sensor channel costs 4 B in the request and 12 B in the reply.
- **DLC quantisation bites.** CAN-FD payloads step 24 → 32 → 48 → 64 (`fw/fdcan.cc:24`). The 40-byte reply goes out as 48; 33 to 48 bytes cost the same.
- **A four-register read is the wrong shape for the fast lane.** If the load cell's *contact flag* were `meas_b` (force-rate moved to `meas_d`), the fast read is two registers: `16 97 04` request, `26 97 04` + 4 reply — 7 B, not 12. Both channels reordered: command 22 → DLC 24, reply 30 → **DLC 32**. One DLC step per node per cycle, for a table edit. The design note's "do not reorder without redoing the bus budget" cuts both ways — this reorder *earns* the redo.

## 3. Cadence, lanes, and the bus budget

Two lanes, one master, strictly poll-response. **Fast lane:** every cycle, one command+query frame per node — stock axis command and query plus each fast channel. **Slow lane:** one node per cycle additionally dumps its full channel set and health; at 13 nodes and 325 Hz that is a 25 Hz refresh per node. Fire-and-forget writes (pixels, tare) fill idle. Promotion from slow to fast is a host schedule change; firmware is untouched.

The spec models a frame as ≈30 µs of arbitration-rate fields plus `(8N+43)` bits at 5 Mbit. **Two corrections are needed before the table is trusted.** `RoundUpDlc` quantises payloads as above. And the model assumes an 11-bit id, but the host sets `0x8000` on every frame that requests a reply (`lib/python/moteus/transport.py:344`) and the firmware sends any id ≥ 2048 as a 29-bit extended frame (`fw/fdcan.cc:323`) — so every fast-lane command is extended, as is every reply from a node with id ≥ 8. The 18 extra id bits plus SRR/IDE at 1 Mbit add roughly **+20 µs per frame** (stuff bits ignored). Recomputed, worst case, all frames extended, slow-lane pair excluded as the spec did:

| Configuration | Cmd / reply DLC | µs per node | 13 nodes @ 325 Hz | Spec said |
|---|---|---|---|---|
| axis only | 16 / 16 | 166 | **70 %** | 55 % |
| axis + 1 input channel (4-reg read) | 20 / 32 | 198 | **84 %** | 65 % |
| axis + 2 input channels (4-reg reads) | 24 / 48 | 230 | **97 %** | 75 % |
| axis + 2 input channels, 2-reg reads | 24 / 32 | 205 | **87 %** | — |
| 2 chains × 7, axis + 1 channel, 400 Hz | 20 / 32 | 198 | **56 %** | 52 % |
| 2 chains × 7, axis + 2 channels, 1 kHz | 24 / 48 | 230 | **161 %** | 130 % |

The spec's two structural conclusions survive, stronger than stated. **Two fast channels per node is the ceiling on one 13-node chain** — with real frame sizes even *one* on every node breaches the 65 % headroom rule. **1 kHz is unreachable on one chain and on two**; 400 Hz on two chains is the right target, and the RC servos are 50–330 Hz devices regardless. Splitting the chain remains the highest-leverage decision: nearly half the load, and fault containment free. Giving ids 1–7 to the nodes that matter most saves ~20 µs on each of their replies.

**Is the two-lane shape right for CATBOT's actual sensors?** Mostly. On a BLDC node the joint angle is already in the stock query (`0x001`), so the channels that earn a fast slot are foot contact, an output-side encoder where the 14:1 belt separates rotor from joint (the site does not say the knees have one), and the *command* side of servos and the SimpleFOC Mini. That is zero to one fast channel on most nodes and two on the shoulders — the budget worry is two nodes, not thirteen. One refinement: schedule each node at a rate divisor (1, 2, 4 … 13) instead of two fixed lanes. Servo-only nodes at half rate cost nothing in firmware and would pull a 13-node chain back under 65 %.

## 4. Host-loss autonomy: G0, G1, G2

The Jetson is "allowed to crash". Three graded answers, only the first mandatory:

- **G0 — independent timeout, always on.** Stock `servo.default_timeout_s` (0.1 s) drops the axis into timeout mode; channels go to `mode = 0`, which is why released is the boot default. No new protocol, no coordination, no shared failure. This is the floor and it is never disabled.
- **G1 — brainstem presence beacon.** A fire-and-forget broadcast to `0x7f` at ~10 Hz; nodes track beacon age in `0x087` and reduce limits when it goes stale. Under 0.1 % of the bus, no election, no node-to-node traffic. **Requires the brainstem to have FDCAN** — §9.
- **G2 — deputy.** If the beacon *also* dies, the node with the lowest non-zero `deputy_rank` waits `rank × stagger_ms` and broadcasts a canned safe sequence. Any host or brainstem traffic demotes it instantly; its authority expires after `authority_ms`.

**G2 is the most dangerous idea in the design, and it should be said plainly.** A node that can command its peers can do so *while it is wrong* — a stuck beacon-age counter, a duplicated rank, a half-dead node that believes the fleet is silent. Three constraints make it survivable and none may be relaxed for convenience: a whitelist of *reducing* actions only (fold, lower, relax, hold — never walk, never raise a limit); authority that *expires* back to G0; and a rank that defaults to 0 so nothing self-promotes. Two things the spec understates. Because moteus ignores the source field, a deputy's frames are indistinguishable from the host's — so **receivers cannot filter a rogue deputy**; a cheap belt-and-braces is to accept a non-host source only while the receiver's own `0x087` ≥ 2. And a broadcast cannot carry per-joint targets, so "fold" must be a *named posture* each node resolves from its own config — those per-joint angles need validating on the standing robot before G2 is ever enabled. Build G0 now, G1 when the brainstem exists, G2 only once CATBOT stands.

## 5. Node identity

A node carries three things that must not be conflated: a **CAN id** (bus address, `id.id`, 1–126), a **UUID** (immutable silicon serial, `0x150–0x153`), and a **name** (`flexnode.name`, 16 NUL-padded UTF-8 bytes at `0x0C0–0x0C3`). The name is in registers, not only a config string, because the text protocol is slow, unavailable to a minimal host, and absent exactly when the name is most wanted — in a fault dump. Four consecutive int32 registers mirror how moteus publishes its UUID, so a name is one subframe, read once at enumeration. The host should assert id, UUID and name against a fleet manifest at boot, alongside profile id and build hash — one refusal catches both a board swapped between joints and a mixed-image fleet. Add `deputy_rank` uniqueness to the same assertion.

## 6. Mapping onto CATBOT

Published fleet: 4× GIM8108-8 "sagittal hips", 6× 5010 knees (14:1 belt), 2× head gimbals on a SimpleFOC dual driver, 7× DS3235/DS3230 servos "hung off node aux ports" — 19 DoF. Aditya's 2026-09-07 statement puts a GIM 8108-8 *and* a SimpleFOC Mini on each of two **shoulder** nodes. I read the shoulders as two of the four GIM8108 nodes (front hips); if they are additional, the site's count of four is wrong. Whether the shoulder Minis *are* the head gimbal driver or a separate pair is stated nowhere.

| Node | Axis 0 | Channels it would declare | Fast-lane load |
|---|---|---|---|
| `shoulder_fl`, `shoulder_fr` | GIM8108-8 | `bldc_ext` (Mini) + `enc_i2c` (Mini feedback) + `imu` + `pixel` + `rail_5v`; one adds `servo_rc` (DS3235), the other has spare capacity ("load cell / RGB") | 2 command channels: cmd 48 / reply 48 — the two heaviest nodes on the bus |
| `hip_rl`, `hip_rr` | GIM8108-8 | `imu`, `pixel`, `rail_5v`, possibly `loadcell` | 0–1 |
| `knee_*` ×6 | 5010 + belt | `imu`, `pixel`; output-side `enc_i2c` and a foot `loadcell` are *plausible but unstated* — which node the foot wires to is undocumented | 0–1 |
| servo nodes | — | `servo_rc` ×1 (+ optional `enc_i2c` feedback), `imu`, `pixel`, `rail_5v` | 1 |

**The 10-vs-13 discrepancy, again.** Ten BLDC actuators get a FlexNode each; the site says thirteen nodes. If 13 = 10 + 3 aux nodes, only 3 of the 7 servos can have dedicated nodes and the other 4 ride on actuator nodes (one is the shoulder's DS3235; three are unknown). If all 7 servos get dedicated nodes, the fleet is 17, and every budget line above gets roughly 30 % worse. This changes the profile mix and the chain split, not the protocol — but it must be settled before the bus is laid out. (The `aux` profile compiles `servo_rc` ×2 against a one-servo-per-node rule; harmless, but worth aligning.)

## 7. Learnings worth keeping

- **`0x7f` broadcast already works.** `fw/moteus.cc:307` accepts `prefix<<16 | 0x7f` on standard and extended filters. G1 and G2 needed no protocol invention.
- **moteus ignores the frame source field**, so a deputy needs no receiver-side change — and that is exactly why a receiver-side sanity check is worth adding (§4).
- **Profiles solved a problem measurement then dissolved.** They were the release valve for a 16.8 kB flash budget; three drive-path-free changes measured −84 kB and a 48.7 kB hole in the linker map was labelled "currently unused". Profiles survive only as a safety/product choice.
- **The PCA9685 was withdrawn** because it optimised a per-node resource (one pulse pin) before asking how the mechanical layout distributed the load (one servo per node, seven nodes). Ask the layout question first.
- **An absent entry in a vendor table is not an absent capability.** "PC13 has no timer" was true of the moteus aux table, false of the silicon (TIM1_CH1N, TIM8_CH4N). Likewise motor PWM is on TIM5, not TIM2 — the conclusion survived, the reasoning did not.
- **Frame cost is not payload length.** DLC steps and the extended-id bit are each worth on the order of 20 % on a small frame; both were missing from the budget (§3).

## 8. Where I disagree, or would push

- **Fix the budget table before anything is scheduled against it** — DLC rounding, extended ids, asymmetric sensor channels. The conclusions hold; the margins do not exist.
- **Put loop-critical measurements first.** Make `meas_a/meas_b` the two registers the fast lane wants for every type (load cell: force, *contact*), so a fast read is a 3-byte request and 7-byte reply. Cheaper to decide now than after the map is public.
- **Eight slots is exactly v1.0's physical ceiling; the address space should not be.** A shoulder with Mini, its encoder, a servo, load cell, IMU, pixel, rail sense and ToF is eight. Reserve `0x210–0x30F` for 16 slots now (free), implement 8, and decide whether onboard fixtures (`imu`, `pixel`, `rail_5v`) consume slots at all — they have v1 aliases, and they eat three of eight on every node if they do. Define `0x085` as *highest populated slot*, not a count, or enumeration stops at the first gap.
- **The 16-register stride suits control-shaped peripherals, not array-shaped ones.** The `imu` binding row is all dashes because six axes do not fit four `meas` registers; its data lives in the v1 alias. Say so, or a second IMU (the head has one) cannot be a channel.
- **Take profiles off CATBOT's critical path.** Space is solved, `full` fits everything, the site already promises "one firmware · N configs", and one image removes the mixed-fleet hazard §6.4 exists to catch. Keep the mechanism for motor-less retail SKUs later.
- **`notes/open-questions.md` is stale** — §2 still says "PC13 has no timer" and "TIM2", §2b still recommends the PCA9685; both contradicted by `hardware-io.md`. Edit in place, as its header asks.
